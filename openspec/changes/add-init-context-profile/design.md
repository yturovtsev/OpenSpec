## Context

See proposal.md — Why.

Two existing mechanisms shape this design:

- **The context channel already exists.** `openspec/config.yaml` carries a `context` string, read by `readProjectConfig` (capped at `MAX_CONTEXT_SIZE`, 50KB) and surfaced to agents as the `context` field of `openspec instructions <artifact> --json`. Nothing new is needed to make agents *read* the profile line; the whole change is about *writing* it.
- **`--language` is the closest precedent.** It validates its value up front (`normalizeLanguage`), formats a fixed block of guidance (`formatLanguageContext`), checks applicability before any file is touched (`assertLanguageCanBeApplied`), and lets `createConfig` write it. `--context-profile` follows the same shape.

The one place the precedent runs out: `--language` **refuses** to touch an existing config, and `serializeConfig` can only build a whole config from scratch. This change requires modifying a config that already exists, which OpenSpec's init has never done.

## Goals / Non-Goals

**Goals:**

- Record the profile line in the project context on both a fresh init and an existing config.
- Preserve everything else in an existing `config.yaml` — comments above all, since `serializeConfig` itself emits a comment-heavy template that users are expected to edit.
- Make repeated `init` runs converge rather than accumulate.

**Non-Goals:**

- Changing how `context` reaches agents. The `context-injection` capability is untouched.
- Teaching the CLI to talk to an MCP server. The flag records a profile *name*; resolving it stays the agent's job.
- Relaxing `--language`'s refusal to modify an existing config. That stays as it is.

## Decisions

### Edit the existing config through the YAML Document API, not a re-serialize

`serializeConfig` builds a fresh document from a `ProjectConfig` object, so routing an update through it would replace the user's file with a generated one — dropping comments, key order, and any field the serializer does not know about.

Parsing with `parseYaml` and re-emitting has the same defect: comments are not part of the parsed value.

**Chosen:** the `yaml` package's `parseDocument` / `doc.toString()` round-trip, which preserves comments and formatting for untouched nodes. `yaml@^2.8.3` is already a direct dependency, so this adds nothing to the install.

*Alternative considered:* textual splicing into the `context: |` block. Rejected — block scalars have indentation indicators, chomping markers, and alternative styles (`>`, quoted, plain), so a text patch has to re-implement a YAML parser to be correct.

### The line is generated by one named formatter and detected by its own prefix

Per the project's design rules ("if we generate it, we track it by name in a constant", "prefer explicit lookups over pattern matching"):

- A `MCP_CONTEXT_PROFILE_NAME` constant holds the MCP server name.
- A `formatContextProfile(profile)` helper — sibling to `formatLanguageContext` — produces the full line.
- A `formatContextProfilePrefix()` helper produces everything up to the profile value. Idempotence and replacement are decided by exact-prefix comparison against each existing context line, not by a regex over the context.

This is what makes "re-running is a no-op" and "a different profile replaces the old line" both fall out of one lookup, and it keeps the emitted text in a single place when the MCP name changes.

### Validation mirrors `normalizeLanguage`

Same rejections, same reason: the value lands verbatim in prompt text. Empty, multiline, control or bidi-control characters, and anything that would push the serialized context past `MAX_CONTEXT_SIZE`.

### Applicability is checked before anything is written

`execute()` already calls `assertLanguageCanBeApplied` early — before legacy cleanup, tool detection, and skill generation — so a bad `--language` value never leaves a half-initialized project. The profile check joins it at the same point: verify the config is readable, parseable, and writable, then fail before the first write.

### `createConfig` gains an `updated` outcome

Its return type is today `'created' | 'exists' | 'skipped'`, consumed by `displaySuccessMessage`. Updating an existing config is a fourth outcome the success message must distinguish, so users can see that init changed a file it normally leaves alone.

### `--language` + `--context-profile` on an existing config still fails

`--language` refuses when a config exists without its exact guidance, and this change does not alter that. So the two flags compose on a fresh init, and the combination still fails on an existing config — because of `--language`, not because of the profile flag. Left as is deliberately: relaxing `--language` is a separate behavioral change that deserves its own proposal.

## Risks / Trade-offs

- **The Document round-trip can still normalize formatting of the node it edits.** → Confine edits to the `context` node; add a test that a config with comments, `rules`, and `operations` survives an update byte-for-byte outside the context block.
- **Line endings.** A CRLF-checked-out `config.yaml` may be re-emitted with `\n`, producing a noisy diff on Windows. → Detect the file's dominant line ending before writing and restore it; cover it in the Windows CI matrix, which already runs the full suite.
- **The profile line is Russian text in a codebase whose other generated guidance is English.** → Accepted: it is the text the team's agents are expected to read. Worth revisiting if the flag is ever upstreamed.
- **Growing init's blast radius.** Init becomes a command that can modify an existing config, which users reasonably assume is safe to re-run. → Mitigated by touching only the `context` node, by idempotence, and by reporting the update in the success output rather than silently.

## Open Questions

None that can be deferred. The MCP server name is required before implementation — it is the literal text agents read — and it is tracked as an open decision in proposal.md rather than here.
